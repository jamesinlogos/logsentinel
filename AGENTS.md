# AGENTS.md — rules for AI agents and operators of LogSentinel

Read before changing code, configuration or infrastructure. Component rules: `inference/AGENTS.md`,
`sentinelcap/AGENTS.md`; this file covers the shared parts, including naming (section 11).

## 1. Map

| Directory | Role | Read first |
|---|---|---|
| `sentinelcap/` | labelled Sysmon capture from the victim VM (the only training data source) | `sentinelcap/AGENTS.md` |
| `inference/` | ransomware detection: Phase 2 rules, Phase 3 model, scheduled and early windows; Kafka in, Kafka out | `inference/AGENTS.md`, `inference/README.md` |
| `notifications/` | worker that sends the Kibana rule's notices to Telegram and Gmail and stores a receipt per channel in Elasticsearch | `notifications/README.md` |
| `config/` | Logstash (`ingest/`, `detection-sink/`), Elasticsearch (pipeline, ILM, template), Kibana (`kibana/`: rule, connector, action), Winlogbeat, Sysmon | `README.md` sections 7, 8, 9.2 and 10.4 |
| `dashboard/` | Kibana dashboards as Dashboard API JSON, generated by `scripts/dashboard_definitions.py` | `README.md` section 9.1 |
| `scripts/` | deployment, backup, stack move, dashboards, alerting, checks (section 9) | script docstrings |
| `docker-compose.yml`, `.env` | backend (Kafka, Elasticsearch, Kibana, 2 Logstash, inference, notifications) and three one-shot init services (`kafka-init`, `elasticsearch-init`, `kibana-init`); `.env` also holds the Kibana key and the Telegram/Gmail credentials | `README.md` section 10 |
| `archives/` | backups (`archives/backups/`), transcripts; not part of the product | — |

New names (file, variable, topic, index, field) follow section 11; `python scripts/check_naming.py` must be clean.

**Check state:** `docker compose ps -a` (all three init services `Exited (0)`, seven services `healthy`),
`bash scripts/healthcheck-all.sh`, `python scripts/verify_detections.py`. Model and threshold in use:
`inference/artifacts/model-meta.json`. Training data: `sentinelcap/captures/`, not the stack. `windows-telemetry-*` and
`ransomware-*` hold only documents from sessions run through this stack; a freshly rebuilt stack has none
(`verify_detections.py`: "no documents yet").

## 2. Data contract

```
Winlogbeat ──> telemetry.windows.sysmon.raw ──> logstash-ingest ──┬──> windows-telemetry-YYYY.MM.dd (ES)
                                                                  └──> telemetry.windows.normalized ──> sentinelcap
                                                                                     │
                                                                                     ▼
                     ┌── security.ransomware.window-scores ──> ransomware-window-scores-YYYY.MM (ES)
inference            ┤
                     └── security.ransomware.detections ─────> ransomware-detections-YYYY.MM (ES)
```

* Every scored window yields a **window score**; one that passes the Phase 2 gate and is reported also yields a
  **detection**. Both come from one `WindowScore` (`scoring.py`; `documents.py` builds the documents) and share `_id` =
  `logsentinel.window.id` = SHA-256 of `host.id` and `event.end`.
* A window is **scheduled** (`logsentinel.window.trigger` `slide`) or **early** (`indicator`: closed at the event
  that brought a new indicator, with the `process.*` of that event). Both are scored and written alike
  (`inference/README.md` sections 4.0, 7).
* **At-least-once with replay**: an input offset is committed only after the broker acknowledges every record of its
  window (`offsets.py`); duplicates overwrite by the fixed `_id`.
* `dynamic: false` on both indices drops fields without a mapping; `tests/test_documents.py` pairs the template with
  real documents to catch this.
* Capture data: `sentinelcap/captures/<run UTC>/<family>/<sample>/`, `format` `.../v1` (section 11.11).
* **Notifications** are a separate branch that Kafka does not feed: a Kibana rule on `ransomware-detections-*` makes the
  Index connector write an envelope to `ransomware-notifications-*`; `notifications` sends it to Telegram and Gmail and
  writes a receipt per channel to `ransomware-notification-deliveries-*` (`README.md` section 9.2). Only Kibana and
  `notifications` write these two families; Logstash writes the other three.

## 3. Invariants

Binding; changing one is the user's decision, not the agent's.

1. **Never run ransomware samples.** `sentinelcap` only copies, extracts and renames; the operator opens files in the
   VM. Goodware scenarios never stop Winlogbeat or Sysmon and never clear Sysmon/Security logs.
2. **Training and evaluation data come only from `sentinelcap`.**
3. **UAC stays on; the operator clicks Yes.** Settled; do not re-propose.
4. **Every number in the documentation traces to tool output** (test, `evaluate`, query, log). No speculation; labels
   are operator-confirmed; the Sysmon configuration is deployed correctly.
5. **Five infrastructure items stay unchanged** to keep the lab simple (TLS/ACL, pickle authentication, scale-out,
   sink durability, Python digest/patch pinning): do not re-propose.
6. **inference never writes to Elasticsearch directly**: Kafka in, Kafka out.
7. **`_id` = `logsentinel.window.id`** and `dynamic: false` mapping (section 2).
8. **Back up before any refactor** (section 8).
9. **No passwords in documentation or logs**: `sentinelcap/config.yaml` has `guest_password`; use the variable
   `SENTINELCAP__VMWARE__GUEST_PASSWORD` instead of writing it to the file.

## 4. Workflows

**Code changes** (in the component directory): `cd inference && make check` (ruff incl. `../scripts`, mypy, pytest; on
Windows run the `Makefile` commands directly, no `make`), `cd sentinelcap && python -m pytest`, `python -m pytest
scripts/tests` (dashboards, alerting and notification setup) and, in `notifications/`, `python -m pytest`,
`python -m ruff check src tests`, `python -m ruff format --check src tests` and `python -m mypy`; then
`python scripts/check_naming.py`.

**Output schema change** (`documents.py`): bump `SCHEMA_VERSION`, the `_meta.schema_version` of the resources in
`config/elasticsearch/` and `SCHEMA_VERSION` in `scripts/verify_detections.py` (a test keeps them equal); edit the
component templates in `config/elasticsearch/`, and `config/logstash/detection-sink/` if `_id` or a topic changes; run
`tests/test_documents.py`; update `inference/README.md` section 7 and section 11.9 here. Indexed documents keep the old
schema: rebuild a clean stack (section 6) or accept both shapes.

**Renaming** something that holds data: section 11.14.

**New capture data:** after each batch run `make model` in `inference` (held-out runs go into `HOLDOUT`) and update
`inference/README.md` section 6. With the Kibana rule and the `notifications` worker installed, a capture through the
stack sends Telegram and Gmail notices (at most one per minute while new detections arrive): disable the rule in Kibana
first if that is unwanted.

**Changes touching the VM or a running stack:** ask first (section 7).

## 5. First deployment

```bash
# .env is provided: set the Docker host's real IP in LOGSENTINEL_KAFKA_ADVERTISED_HOST; Kibana key and Telegram/Gmail settings: README.md 9.2
docker compose up -d      # kafka-init creates 4 topics; elasticsearch-init installs pipeline, ILM, component and index templates; kibana-init installs the alerting rule and notification action (`--apply`)
bash scripts/healthcheck-all.sh
```

* Both Logstash services start after `kafka-init` and `elasticsearch-init` exit 0 (`depends_on` with
  `service_completed_successfully`), so no index precedes its template. `inference` waits for `kafka-init`;
  `notifications` waits for `elasticsearch-init` and `kibana-init`.
* Init services rerun idempotently on every `docker compose up -d`: fresh Kafka or Elasticsearch volumes need no manual
  step. `scripts/create-topics.sh`, `scripts/init-elasticsearch.sh` and `scripts/init-kibana.sh` can still be run by hand (after editing
  `config/elasticsearch/`).
* `notifications` starts with `docker compose up -d`; without the Telegram and Gmail settings of `.env` it restarts
  (exit code 2), and with them it sends every envelope that has no receipt yet (`notifications/README.md`).
* Dashboards, rule and connector are installed with the `*_setup.py` tools (`README.md` sections 9.1 and 9.2); `--apply`
  changes Kibana and needs the user's consent (section 7).
* Init exits 0 after about 30 s; the six services that existed before `notifications` were `healthy` after about 77 s
  (`inference/README.md` section 9.3; that measurement does not include the worker).
* Fresh volumes have no Kibana data view: create it via the API (section 6, step 6).
* Install Sysmon and Winlogbeat on the VM per `README.md` sections 10.3 and 10.4.

**Redeploy a new build (keeping data)** after changing code, configuration or the model:

* `docker compose up -d --build` (ask first if the stack is running, section 7); Compose recreates services whose image
  or configuration changed.
* `inference/artifacts/` is mounted read-only: a new model needs the `inference` container recreated.
* `config/logstash/**` is mounted into the Logstash containers: after editing a filter or pipeline run
  `docker compose restart logstash-ingest`.
* A renamed service leaves its old container (own `container_name`) as an orphan: add `--remove-orphans`.
* Do not delete volumes.
* A changed Telegram or Gmail value in `.env` recreates `notifications`; a changed Kibana key recreates `kibana` and
  must not happen after rules exist (`README.md` section 9.2).

**Move the stack to another machine** (the VM is set up there already; Docker and Python run on both):

```bash
python scripts/migrate_stack.py export --out <new directory>      # source: stack up, VM off; stops the stack for the copy
python <copy of that directory>/tools/migrate_stack.py import --source <copy> --target <new project directory> --kafka-host <ip>
```

* `export` records the document count of every data index and the Kafka end offsets, stops the stack, writes the
  three volumes and the project (with `sentinelcap/config.yaml`, which has the source machine's VMware paths and
  `guest_password`: keep the export private) with `MANIFEST.json` and `SHA256SUMS`, and starts the stack again. It leaves
  out `sentinelcap/captures`, `sentinelcap/samples`, `archives` and `.venv`. Options: `--images` (offline target),
  `--leave-stopped`.
* `import` verifies the sums, refuses a non-empty target directory, existing containers or non-empty volumes
  (`--replace-volumes` empties them), sets `LOGSENTINEL_KAFKA_ADVERTISED_HOST` to `--kafka-host`, restores the volumes,
  starts the stack and compares counts and offsets with the source (exit 1 on a difference).
* By hand afterwards: the Winlogbeat output host in the VM snapshots must reach the new Kafka host, and
  `sentinelcap/config.yaml` needs the VMware paths of the new machine (the export carries the old ones).
* The project archive carries `.env`: the Kibana key (the rule and connector in the Elasticsearch volume are encrypted
  with it; keep it unchanged) and the Telegram and Gmail credentials. Use `--leave-stopped` for a cutover, so that two
  copies do not both send notifications. Keep the export directory outside the project (`export` refuses otherwise).
  A Windows target: `README.md` section 10.5.

## 6. Clean-stack rebuild

Discards all stack data and rebuilds (e.g. after an output schema change). The user must state explicitly: delete
volumes, no restore, VM off. Consent is per run (section 7).

**Preconditions:** `docker compose ps` all healthy; all consumer groups at lag 0 (`scripts/healthcheck-all.sh`); at
least 5 GB free; `python scripts/check_logstash_config.py` passes; backup with
`python scripts/backup_project.py --label <label> --stack`, then `--verify archives/backups/<directory just created>`
(`--stack` also writes the `ransomware-*` documents to `es-ransomware-documents.ndjson`).

1. VM off, raw topic silent: no `vmware-vmx` process, `sentinelcap-capture-*` groups gone,
   `kafka-get-offsets.sh --topic telemetry.windows.sysmon.raw` unchanged for 15 s.
2. Record container volumes (`docker inspect`, anonymous ones too); tag the service image:
   `docker tag logsentinel-inference:latest logsentinel-inference:backup-<UTC>`.
3. `docker compose down` (keep volumes), then `docker volume rm` exactly the 3 named volumes
   (`logsentinel_kafka-data`, `logsentinel_elasticsearch-data`, `logsentinel_logstash-ingest-data`) and the anonymous
   ones from step 2. Never `docker volume prune`: Docker holds other projects' volumes.
4. `docker compose up -d --build`. `create-topics.sh`, `init-elasticsearch.sh` and `init-kibana.sh` are unnecessary: the init services do
   that and Logstash starts only after them.
5. Wait for all three init services `Exited (0)` and seven services `healthy` (`docker ps -a`).
6. Kibana data views: `POST /api/data_views/data_view` (header `kbn-xsrf: true`), one per `title`
   (`windows-telemetry-*`, `ransomware-detections-*`, `ransomware-window-scores-*`); `name` = index family name,
   `timeFieldName` = `@timestamp`. The volume held Kibana's saved objects, so dashboards, rule and connector are gone
   too: install them again from `README.md` sections 9.1 and 9.2 if the new stack should have them.
7. Verify: `python scripts/verify_detections.py` (12 resources OK, "no documents yet") and
   `bash scripts/healthcheck-all.sh`; then
   `cd inference && python -m training.e2e_restart --capture ../sentinelcap/captures/<run>/blackbasta/<sample> --bootstrap localhost:9092`
   (kill -9; own self-deleting topic). Delete leftover `e2e-*` consumer groups:
   `kafka-consumer-groups.sh --delete --group <group>` (a just-killed process's group is deletable only after its member
   expires).

**Rollback:** `docker compose down`; restore `docker-compose.yml`, `.env`, `config/`, `scripts/` and `inference/` from
the `repo.tar.gz` of the backup taken right before the run (section 8); re-tag the image
(`docker tag ...:backup-<UTC> ...:latest`); `docker compose up -d`. Deleted data cannot be recovered.

## 7. Ask the user first

* stopping, recreating or `docker compose up` on a running stack; any change while the VM is capturing;
* deleting anything: volumes, networks, indices, images, backups, capture data, old configuration files;
* replaying a session into a real topic or writing to a real index (`replay_to_kafka.py`);
* changing Winlogbeat/Sysmon configuration in the VM or retaking a snapshot;
* changing Kibana (`alerting_setup.py`, `notification_setup.py`, `dashboard_setup.py` with `--apply`; `docker compose up -d` runs the first two through `kibana-init`) or sending a test
  notice (`notification_test.py --enqueue`: real Telegram and Gmail messages);
* sending data off the machine (external services, uploads).

Consent covers one action, not similar later ones.

## 8. Backup and restore

```bash
python scripts/backup_project.py --label <kebab-label> [--captures] [--stack]
python scripts/backup_project.py --verify archives/backups/<directory>
```

`archives/backups/<UTC>-<label>/` contains:

* `repo.tar.gz`: code, configuration, documentation, `.env`, artifacts, fixtures; excludes `.venv`, caches, `captures`,
  `samples` (malware: antivirus blocks reads), `archives`;
* `captures.tar.gz` (`--captures`);
* `stack/` (`--stack`): templates, ILM, pipelines, mappings, `_cat/indices`, Kibana saved objects, Docker, Kafka offsets;
* `SHA256SUMS` and `MANIFEST.json` (label, UTC time, per-file checksums).

The tool refuses to run with under 5 GB free. Elasticsearch and Kafka data are not copied (they live in Docker
volumes). Restore code: `tar -xzf repo.tar.gz -C <target directory>`; captures:
`tar -xzf captures.tar.gz -C sentinelcap/captures`.

**Git.** The repository is under git; `origin` is `https://github.com/jamesinlogos/logsentinel.git`, branch `main`.
`.gitignore` leaves out `.venv`, caches, `archives/`, `sentinelcap/captures`, `sentinelcap/samples` (malware) and
stack exports; `.gitattributes` turns line-ending conversion off, so files keep the endings of section 10 whatever
`core.autocrlf` says. `.env` and `sentinelcap/config.yaml` are committed without credentials (`.env`: the Kibana key
and the Telegram/Gmail values blank; `config.yaml`: `guest_password: 'CHANGE_ME'`); the working copies hold the real
values and carry `git update-index --skip-worktree`, which keeps them out of `git add -A` and `git commit -a`. After a
fresh clone fill the values in and set the flag again; never `git add -f` them. Commits carry no stack or capture
data. A push sends data off the machine: ask first (section 7).

## 10. Known traps

* Windows `Path.write_text` writes `\r\n`: patch scripts must keep each file's line endings (Linux-run files — `.sh`,
  `Dockerfile`, `Makefile`, YAML, `.conf` — are always LF: `.editorconfig`).
* Git Bash heredocs drop `\`: write scripts with regexes or Windows paths using a file-writing tool. Convert Windows
  paths for Python with `cygpath -w`.
* Deleting or renaming a bind-mounted file makes Docker create a **directory** of that name at the next container
  start; delete only after Compose points to the new file.
* Reading a file in `sentinelcap/samples/` (e.g. with the backup tool) can trigger Windows Defender; opening it then
  fails with `OSError 22` ("file contains a virus"). The directory is excluded from backups; do not read samples with
  any tool other than `sentinelcap`.
* `.env` holds secrets (Kibana key, Telegram token, Gmail App Password): never print them. `docker compose config` shows
  them (use `--quiet`); `backup_project.py` archives and `migrate_stack.py` exports include `.env`: keep those private.
* A directory such as `logsentinel-migration/` inside the project root is archived by `backup_project.py` (2.3 GB with
  `images.tar`) and fails `check_naming.py`: keep exports outside the project.
* `training_rows` seeds window sampling with the run name: renaming a run shifts `evaluate` figures slightly
  (`inference/README.md` section 6).

## 11. Naming rules

Single source for the name of everything: files, code, configuration, environment variables, Kafka topics,
Elasticsearch indices, document fields, log records, Docker names, capture data. Read it
**before creating a new name**. `scripts/check_naming.py` checks the machine-checkable rules; every deviation must be
in the exceptions list (section 11.13).

### 11.1 Principles

1. **Upstream standard first**: ECS (document fields), Sysmon (`winlog.*`), Kafka, PEP 8, Docker Compose, Elastic.
   Invent a name only when none exists.
2. **One concept, one name** (sections 11.2, 11.12); other forms derive mechanically from the slug.
3. Name **what the thing is**: a noun, never a verb (`deploy.md` is wrong); no history (`new`, `old`, `final`, version
   numbers); no abbreviations (except `id`, `ip`, `sha256`, upstream names); no local time.
4. Lowercase ASCII. Every exception is registered in section 11.13 with a reason and a review condition.
5. Renaming anything that holds data follows section 11.14.

### 11.2 Slugs and derived forms

| Concept | Slug | Python package / module | Env var prefix | Prose |
|---|---|---|---|---|
| Product | `logsentinel` | — | `LOGSENTINEL_` | LogSentinel |
| Capture tool | `sentinelcap` | `sentinelcap` | `SENTINELCAP__` | SentinelCap |
| Detection service | `inference` | `inference` | `INFERENCE__` | inference |
| Notification sender | `notifications` | `notifications` | `LOGSENTINEL_` (section 11.13) | notifications |
| Infrastructure | `kafka`, `elasticsearch`, `kibana`, `logstash-ingest`, `logstash-detection-sink` | — | — | the component's own name |

Directories, Compose services, images, consumer groups and `service.name` use the slug (kebab-case); containers are
`logsentinel-<service>`; Python packages use snake_case.

### 11.3 Files and directories

* Directories and non-Python files: **kebab-case** (`create-topics.sh`, `model-meta.json`, `sink-inference.conf`);
  Python files and packages: **snake_case** (`backup_project.py`).
* Tool-convention names stay: `README.md`, `AGENTS.md`, `LICENSE`, `Makefile`, `Dockerfile`, `.env`, `.gitkeep`, `.gitignore`, `.gitattributes`, `.dockerignore`,
  `pyproject.toml`, `__init__.py`, `__main__.py`.
* **The only markdown files are `README.md`** (what a component is, usage, design, measurements) **and `AGENTS.md`**
  (rules for people and AI agents who keep changing it); at most these two per component directory, no other markdown
  (checked by `scripts/check_naming.py`, rule `document`).
* Configuration resources carry their own name: `config/elasticsearch/<kind>/<name>.json` installs as `<name>`;
  `scripts/init-elasticsearch.sh` needs no name table.
* **Timestamps in names are UTC `YYYYMMDDTHHMMSSZ`** (ISO 8601 basic): SentinelCap run directories, backup manifests,
  backup directories, model `version`. Index names follow Elastic (`YYYY.MM`, `YYYY.MM.dd`, section 11.8).

### 11.4 Python

* PEP 8 and `ruff` rule group `N` (required in `make check`); exception classes end in `Error`.
* Units go in the name when not obvious: time `_sec`, size `_bytes` (`idle_flush_sec`, not `idle_flush_seconds`).
* No abbreviations in the public API (except `id`, `ip`, `sha256`).
* `session_path` is one session's path under the captures directory; `session_id` means only the UUID in
  `metadata.json`.

### 11.5 Configuration and environment variables

* YAML keys: snake_case, naming what they point to (`detections_topic`, `window_scores_topic`).
* **Stack-wide variables** (`.env`, `docker-compose.yml`, `scripts/*.sh`): `LOGSENTINEL_<NAME>`.
* **Component configuration overrides:** `<COMPONENT>__<SECTION>__<KEY>`, double underscore between segments
  (`INFERENCE__KAFKA__BOOTSTRAP_SERVERS`, `SENTINELCAP__VMWARE__GUEST_PASSWORD`). Component scalar variable:
  `<COMPONENT>_CONFIG` (`INFERENCE_CONFIG`, the configuration file path).
* inference logging: `INFERENCE__LOG__LEVEL` and `...__LOG__FORMAT` (`logs.py` reads the `LOG` section before the
  configuration loads).
* Upstream-defined variables stay as they are (`KAFKA_*` in the broker container, `ES_JAVA_OPTS` in the Elasticsearch
  container, `discovery.type`, `xpack.*`, `ELASTICSEARCH_HOSTS`, `XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY` in the Kibana
  container).
* Logstash plugin `id`: kebab-case, says what the plugin does, unique in the pipeline (`user-split`, `registry-hive`,
  `hashes-process`). Every grok, dissect, translate and kv has an `id` so the monitoring API can name each filter
  (checked by `test_stack_config.py`).

### 11.6 CLI and CSV

* Kebab-case flags, one per concept: `--family`, `--sample` (SHA-256 of the executable, script name or session code),
  `--label` (`0` benign, `1` ransomware), `--duration`, `--force`.
* CSV headers snake_case: `family,sample,path,label`.

### 11.7 Kafka

* Topic: `<domain>.<subject>.<dataset>`, lowercase, dots between levels, hyphens inside multi-word segments; domain
  `telemetry` (observed data) or `security` (system conclusions).
* Consumer group: service slug, plus `-<purpose>` when a service has several (`logstash-detection-sink-window-scores`).
* Never rename a topic that holds data: create a new one and migrate (section 11.14).

| Topic | Content | Key | Partitions |
|---|---|---|---|
| `telemetry.windows.sysmon.raw` | raw Sysmon events from Winlogbeat | `host.name` | 3 |
| `telemetry.windows.normalized` | normalized events (`format` v1) | `host.name` | 3 |
| `security.ransomware.detections` | detections (windows that pass the Phase 2 gate and are reported) | `host.id` | 3 |
| `security.ransomware.window-scores` | every scored window, with features | `host.id` | 3 |

### 11.8 Elasticsearch

* Index: `<domain>-<plural dataset>-<period>`; period by volume: **daily** (`YYYY.MM.dd`) for telemetry only,
  **monthly** (`YYYY.MM`) for the rest. No data streams: replays must overwrite by `_id`, which data streams do not
  allow for existing documents.
* Index templates, ILM policies and ingest pipelines are named after the index family (`ransomware-detections`);
  shared ones `logsentinel-<purpose>` (`logsentinel-window-score`, `logsentinel-event-ingested`).
* No version numbers in names; the version is in `_meta.schema_version` and `logsentinel.schema_version`.

| Index family | Period | Written by | Retention |
|---|---|---|---|
| `windows-telemetry-*` | daily | `logstash-ingest` (`sink-es`) | — |
| `ransomware-detections-*` | monthly | `logstash-detection-sink` (pipeline `detections`) | 365 days |
| `ransomware-window-scores-*` | monthly | `logstash-detection-sink` (pipeline `window-scores`) | 90 days |
| `ransomware-notifications-*` | monthly | Kibana Index connector | 90 days |
| `ransomware-notification-deliveries-*` | monthly | `notifications` | 90 days |

`_id` of the detection and window-score families is `logsentinel.window.id`: a window's detection and window score share it across the
two indices. ILM counts `min_age` from creation of the monthly index, so actual retention exceeds the figures by up to
one month.

### 11.9 Document and log-record fields

1. **ECS names first**: a field that exists in ECS uses its exact name and meaning (`@timestamp`, `event.*`, `host.*`,
   `service.*`, `threat.*`, `error.*`, `log.*`).
2. `winlog.*`, `sysmon.*`, `agent.*`, `rule.name` stay unchanged (Winlogbeat/Sysmon schema; PascalCase in
   `winlog.event_data.*` is Sysmon's).
3. **Every other field is `logsentinel.<object>.<property>`**; no custom top-level fields.
4. snake_case; scalars singular, arrays plural (`indicators`).
5. Booleans are adjectives or participles, no `is_`: `gated`, `suspicious`, `reported`.
6. Units in the name when ECS defines none (`uptime_sec`, `down_sec`). No repeated words
   (`logsentinel.verdict.scores.model`, not `score_components.model_score`).
7. Elasticsearch documents require `@timestamp`, `ecs.version`, `event.kind`, `event.module`, `event.dataset` and
   `logsentinel.schema_version`.
8. Transient values stay in the process: use Logstash `[@metadata]`.
9. An absent value omits the field; never `null`.

### 11.10 Docker and Compose

* `docker-compose.yml` has `name: logsentinel`; a service is the component slug; a container is `logsentinel-<service>`.
* One network `backend`; volumes `<service>-data` (`kafka-data`, `elasticsearch-data`, `logstash-ingest-data`); anchors
  `x-<purpose>` (`x-logging`, `x-kafka-image`, `x-elasticsearch-image`). Compose prefixes the project name
  (`logsentinel_backend`).
* Every container has a log limit (`x-logging`).
* A one-shot init job is the service `<service>-init` of the service it initializes (`kafka-init`,
  `elasticsearch-init`): container `logsentinel-<service>-init`, `restart: "no"`; dependents wait with `depends_on` and
  `condition: service_completed_successfully`.
* A default after `:-` in `docker-compose.yml` equals the value in `.env` (test `test_compose_defaults_equal_the_env_file`).

### 11.11 SentinelCap capture data

* Path: `captures/<run>/<family>/<sample>/`: `<run>` UTC `YYYYMMDDTHHMMSSZ`, `<family>` lowercase, `<sample>` lowercase
  SHA-256, script name or session code.
* `metadata.json` keys snake_case; `format` = `logsentinel.normalized-sysmon.jsonl/v<N>`; bump `N` when the event or
  metadata schema changes. Now `v1`: events have no `@version`, MITRE data is in `threat.*`, the label is in
  `label.target_class` and `label.target_class_name`.

### 11.12 Glossary

One meaning per word; code and documentation use exactly this meaning.

| Term | Meaning |
|---|---|
| **window** | 60 s span of one host's events: scheduled or early |
| **scheduled window** | a window whose end is on the 10 s grid (`logsentinel.window.trigger` `slide`); closed by the next event past its end or by the idle flush |
| **early window** | a window closed at the event that brings a new indicator, ending 1 ms after it (`logsentinel.window.trigger` `indicator`) |
| **window score** | the service's result for one window; every window has one |
| **detection** | a window score that passed the Phase 2 gate and is reported after suppression |
| **verdict** | the judgement part of a record: `gated`, `suspicious`, `reported`, label, scores |
| **indicator** | one Phase 2 rule (`shadow_copy_deletion`, ...) |
| **sample** | the thing that is run: an executable (SHA-256), script or session code |
| **family** | a ransomware family, or `goodware`, `idle` |
| **run** | one `run`/`batch`/`capture` execution; one UTC directory |
| **session** | the data of one sample in one run (`<run>/<family>/<sample>/`) |
| **label** | `0` benign, `1` ransomware, assigned by the operator |
| **monitored host** | the machine being monitored (`host.id`) |

### 11.14 Renaming something that holds data

1. `python scripts/backup_project.py --label <label>` (add `--captures` when capture data is affected, `--stack` when
   Elasticsearch/Kafka is), then `--verify` the directory just created.
2. Change code, configuration, documentation and tests together.
3. Data already written under the old name (captures, indices, topics) does not follow: migrate or recreate each item
   explicitly and verify record by record; never rename a topic or index that holds data in place.
4. `python scripts/check_naming.py` and `make check` must be clean.
